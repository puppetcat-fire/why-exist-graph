# why-exist-graph 设计模式参考（0.5.0）

## 怎么用这份文件

本文件的权威是 `scripts/wxg_contract.py` 与由它生成的 `references/contract.md`；这里只回答“什么时候把某个模式写进图、怎么写”。固定三步：

1. 按第 1 节判断该不该建 `pattern` 节点；不满足就只记理由，不建节点。
2. 按第 2 节挑候选，读对应小节，抄 JSON 骨架，把 id、`src` 与 attrs 换成当前 feature 的真实值。
3. 写图前确认：`applicability` 与 `not_applicable` 非空；`applies` 的 `src` 是图里已存在的 `component`、`classifier` 或 `operation`；`dst` 是本 feature 或本仓的 `pattern` 节点。

pattern 是设计决策节点，不是装饰。

- 每个 pattern 必须通过 `applies` 边挂到具体设计元素上，方向是“具体设计元素 -> pattern”。作用域内每个 pattern 至少要有一条这样的入边，否则 gate 直接 FAIL。
- gate 对 pattern 只做机械检查：`applicability` / `not_applicable` 非空、存在 `applies` 入边。它不评价模式选得对不对。
- 选得对不对由咬合回答：UNNECESSARY 判误用与过度应用，HOLLOW 判空壳实现，DOC-ONLY 判“图里有、代码里没有”，UNMAPPED 判映射不上，UNKNOWN 判证据不足，KEEP 判成立。gate 采信每个节点当前代最新一条咬合；KEEP 只反证同一节点，A 的 KEEP 不能抵消 B 的 UNNECESSARY。
- 04 架构视图会包含作用域内的 pattern 行（kind、id、名称），所以 `name` 写模式名本身（如 `Strategy`），不写“支付策略封装”这类局部描述。

节点 id 形如 `pattern:<feature>:<slug>` 或 `pattern:<repo>:<slug>`：单 feature 内新建用前者，跨 feature 共用的仓级约定用后者。attrs 允许的键：`applicability`、`not_applicable`（两者必填非空）、`intent`、`forces`、`cost`、`alternative`、`source`，以及 `x_*` 扩展键。

## 1. 有限应用原则

1. 变化点已真实出现才用：至少能指出两处不同实现或两次同一原因的需求变更，指不出就不建 pattern 节点。
2. 重复与耦合要举出具体证据：点名重复的函数、文件与耦合的调用点，证据写进 `x_evidence` 或 `intent`，写不出位置就说明变化点不成立。
3. 先删后抽象：先内联或删除重复，删不掉的部分才由模式解释，不用模式给本该删除的代码发证书。
4. 一个变化轴最多一个主模式：同一组会一起改动的实现只由一个模式承担选型，第二个模式必须用 `x_composition` 写出它服务的另一条轴，写不出就按过度应用处理。
5. 不预付未来需求（YAGNI）：只有当前 feature 的验收用例需要的变化点才算数，未来需求写进 `not_applicable` 或另开 feature，不写进 `applicability`。
6. 组合模式必须显式写理由：组合时每个 pattern 的 `intent` 要写清它负责哪一段，`x_composition` 要写清协作顺序与边界，没有理由的组合按 UNNECESSARY 处理。
7. 引入模式必须同时写不适用边界与替代方案：`not_applicable` 要具体到“用了会怎样”，`alternative` 要给出一个更简单的替代；缺 `applicability` 或 `not_applicable` 时 gate 直接 FAIL，缺 `alternative` 由 audit 与咬合追。

这 7 条里，gate 只机械执行第 7 条的前半（`applicability` / `not_applicable` 非空）与 `applies` 入边存在；第 1 至 6 条由 audit 角色读 attrs 判定，并以咬合判决兜底。

## 2. 模式目录

| 模式 | 类别 | 一句话意图 | 典型适用信号 | 默认结论 |
|---|---|---|---|---|
| Factory Method | 创建型 | 把产品选型推迟到工厂方法，调用方只依赖产品抽象。 | 同一产品抽象有 2 个以上实现，选型由配置或上下文决定。 | 慎用 |
| Builder | 创建型 | 分步组装复杂对象，把构造过程与表示分开。 | 参数 4 个以上、可选件多、存在多种真实组合。 | 用 |
| Singleton | 创建型 | 保证进程内唯一实例并提供访问点。 | 进程级独占资源，重复创建会破坏正确性。 | 慎用（默认不用） |
| Adapter | 结构型 | 把已有接口转换成调用方期望的接口。 | 外部接口不可改，转换在 2 处以上重复。 | 用 |
| Facade | 结构型 | 为一组子系统提供统一的高层入口。 | 一个用例按固定顺序调用 3 个以上子系统。 | 慎用 |
| Decorator | 结构型 | 用包装对象叠加行为而不改原对象。 | 同一横切行为需要按组合叠加到多个实现。 | 慎用 |
| Proxy | 结构型 | 用代理控制对真实对象的访问。 | 懒加载、权限、远程访问或引用计数。 | 慎用 |
| Strategy | 行为型 | 把可互换算法封装成对象，运行期选择。 | 同一决策点有 2 个以上算法且会继续增加。 | 用 |
| Observer | 行为型 | 主题变化时通知多个订阅者。 | 一个事件有 2 个以上互不相关的消费者。 | 慎用 |
| Template Method | 行为型 | 基类固定骨架，子类实现可变步骤。 | 多个流程共享 3 步以上骨架，差异只在少数步骤。 | 慎用 |
| State | 行为型 | 把状态相关行为拆成状态对象。 | 3 个以上状态且同一操作在不同状态下行为不同。 | 慎用 |
| Command | 行为型 | 把请求封装成对象以排队、记录与撤销。 | 操作需要排队、重放、撤销或多种触发来源。 | 慎用 |
| Repository | 架构与集成 | 用集合接口表达聚合的持久化边界。 | 聚合根明确，用例只按聚合存取，需要内存实现。 | 慎用 |
| Unit of Work | 架构与集成 | 一次事务内跟踪变更，提交时统一写回。 | 一个用例修改 2 个以上聚合且必须同成同败。 | 慎用 |
| Ports & Adapters | 架构与集成 | 核心依赖端口，适配器实现外部交互。 | 核心要脱离真实外部系统测试，依赖会替换。 | 用 |
| Circuit Breaker | 架构与集成 | 下游连续失败时快速失败并短路。 | 跨进程调用，下游故障会拖垮调用方，且有降级。 | 慎用 |

默认结论是起点，不是许可：“用”表示适用条件有证据时默认建节点；“慎用”表示默认不建，只有当适用条件逐条有证据、不适用边界也写清楚时才建。

## 3. 创建型

### Factory Method

**意图**：定义创建产品的接口，让工厂方法决定实例化哪个具体产品；调用方只依赖产品抽象。

**适用条件**：
- 同一产品抽象有 2 个以上具体实现，且选型由配置、环境或请求上下文决定（能指出具体配置项或请求字段）。
- 创建逻辑在 2 个以上调用点重复（能列出文件与位置）。
- 产品构造需要统一初始化或依赖注入，这些步骤不该散落在调用方。
- 产品选型在运行期可能变化，调用方不应在编译期绑定具体类。

**不适用边界**：
- 只有一种实现：工厂退化为一次多余的间接调用，读代码要先跳两层才看到真实构造。
- 选型只在进程启动时发生一次：模块级字典映射或显式构造更直接，工厂只增加维护面。
- 构造参数随产品差异巨大：统一签名会把差异挤进可选参数或字典，类型检查失效。

**代价与替代**：代价是多一层抽象与一个命名点，调试要多跳一步。更简单的替代是先用 `{"x": XImpl, "y": YImpl}[kind]()` 这类映射函数选型；等第二个产品真的出现、且选型点在 2 处以上，再抽工厂接口。

**wxg 建模示例**：

```json
{
  "node": {
    "id": "pattern:feat-pricing:factory-method",
    "kind": "pattern",
    "name": "Factory Method",
    "attrs": {
      "intent": "把产品选型推迟到工厂方法，调用方只依赖计价接口。",
      "applicability": "同一计价接口有 2 个实现（标准价/会员价）；选型由请求里的 customer_tier 决定；构造逻辑在 price_order 与 quote_preview 两处重复。",
      "not_applicable": "只有标准价一种实现时不用；选型只在进程启动时发生一次时不用；两个实现的构造参数差异大于共性时不用，否则统一签名会把差异挤进可选参数。",
      "forces": "选型变化 vs 调用方稳定；构造初始化 vs 调用点简洁。",
      "cost": "多一个工厂抽象与一次间接调用，调试要多跳一层。",
      "alternative": "先用 {tier: price_fn} 字典映射在 price_order 内部选型；第二处调用点出现且选型继续增长时再抽工厂接口。",
      "source": "GoF (1994)"
    }
  },
  "edge": {
    "kind": "applies",
    "src": "operation:feat-pricing:price_order",
    "dst": "pattern:feat-pricing:factory-method"
  }
}
```
- 咬合示例：若 `price_order` 只有一个实现分支、全仓也只有这一处构造点，判 UNNECESSARY；若图里有该 pattern 节点、代码里既没有产品接口也没有工厂方法，判 DOC-ONLY。

### Builder

**意图**：把复杂对象的构造过程与最终表示分开，用分步或链式调用组装，在 `build()` 一次性校验并产出对象。

**适用条件**：
- 构造参数 4 个以上，其中 2 个以上可选，且能举出 2 种以上真实参数组合。
- 同一产品有 2 个以上构造入口（不同预设或不同来源），重复拼装同一组参数。
- 构造有顺序或组合约束（缺字段、互斥字段），调用方不应各自校验。
- 目标对象构造完即不可变，后续不再改字段。

**不适用边界**：
- 参数少且全必填：直接构造或 dataclass 默认值更清楚，Builder 会把 3 行变成 10 行。
- 只有一种固定组合：写一个具名工厂函数（`default_client()`）就够。
- 组装步骤随调用方发散到无法收敛：Builder 会变成半个 DSL，校验分散，最后仍需总校验。

**代价与替代**：代价是多一个 builder 类型与一份字段映射，`build()` 之前对象处于半成品状态。更简单的替代是关键字参数加 dataclass 默认值，或 `make_report(**overrides)` 函数；等参数超过 4 个、组合真实出现且需要统一校验时再上 Builder。

**wxg 建模示例**：

```json
{
  "node": {
    "id": "pattern:feat-report:builder",
    "kind": "pattern",
    "name": "Builder",
    "attrs": {
      "intent": "分步组装报表导出配置，在 build() 统一校验并产出不可变对象。",
      "applicability": "导出配置有 7 个字段，其中 4 个可选；存在 full 与 incremental 两种真实组合；两处入口重复拼同一组默认值；缺字段必须在构造时拒绝。",
      "not_applicable": "参数少于 4 个且全必填时不用，直接构造更短；只有一种固定组合时不用，具名工厂函数就够；组装步骤随调用方发散时不用，Builder 会变成半个 DSL，校验仍然分散。",
      "forces": "构造可读性 vs 类型安全；默认值与校验集中 vs 调用点灵活。",
      "cost": "多一个 builder 类型与一份字段映射，build() 之前对象处于半成品状态。",
      "alternative": "先用关键字参数加 dataclass 默认值，或 make_report(**overrides) 函数；参数超过 4 个且组合真实出现时再上 Builder。",
      "source": "GoF (1994)"
    }
  },
  "edge": {
    "kind": "applies",
    "src": "classifier:feat-report:report_builder",
    "dst": "pattern:feat-report:builder"
  }
}
```
- 咬合示例：若导出配置只有 3 个必填参数、全仓只有一种组合，判 UNNECESSARY；若图里有 builder 节点、代码里只有 dataclass 没有 `build()` 校验，判 DOC-ONLY。

### Singleton

**意图**：保证一个类在进程内只有一个实例并提供访问点；默认结论是不用。

**适用条件**（只有以下同时成立才用）：
- 资源在进程内必须唯一，重复创建会直接破坏正确性（独占设备句柄、进程级注册表），能指出重复创建的失败方式。
- 生命周期必须覆盖整个进程，且无法在组合根一次构造后注入。
- 初始化有并发约束（首次访问初始化、多线程只初始化一次），且有可验证的并发测试。

**不适用边界**：
- 只是为了“到处能拿到”：全局可变状态让单测无法隔离，测试之间通过它串味。
- 用来传配置或连接：改为在组合根构造、按参数注入；需要默认值时用模块级常量。
- 需要按请求或租户隔离：单例直接把隔离打破，只能再补一层请求上下文。

**代价与替代**：代价是隐式依赖、测试污染、并发初始化坑，以及“改一处影响全局”的耦合。更简单的替代是依赖注入（构造参数）加组合根持有唯一实例；确实需要全局访问时用显式注册表函数（`get_app_config()`），不用类属性。Singleton 的默认结论是不用：能注入就注入，注入不了先问为什么。

**wxg 建模示例**：

```json
{
  "node": {
    "id": "pattern:feat-config:singleton",
    "kind": "pattern",
    "name": "Singleton",
    "attrs": {
      "intent": "保证进程内只有一个配置快照并提供访问点；默认不用。",
      "applicability": "配置快照在进程内必须独占同一份；重复加载会读到不一致的值；生命周期覆盖整个进程且无法在组合根一次注入；首次访问的并发初始化有测试覆盖。",
      "not_applicable": "只是为了到处能拿到时不用，全局可变状态会让测试互相污染；用来传配置或连接时不用，改在组合根构造并按参数注入；需要按请求或租户隔离时不用，单例会直接打破隔离。",
      "forces": "全局访问便利 vs 测试隔离；唯一实例 vs 可替换依赖。",
      "cost": "隐式依赖、测试污染、并发初始化坑，改一处影响全局。",
      "alternative": "依赖注入（构造参数）加组合根持有唯一实例；确实需要全局访问时用显式注册表函数 get_app_config()，不用类属性。",
      "source": "GoF (1994)"
    }
  },
  "edge": {
    "kind": "applies",
    "src": "classifier:feat-config:app_config",
    "dst": "pattern:feat-config:singleton"
  }
}
```
- 咬合示例：若 `app_config` 是普通类加模块级变量、没有唯一实例保证，判 DOC-ONLY；若业务对象本可注入却用单例取全局状态，判 UNNECESSARY（替代是构造注入）。

## 4. 结构型

### Adapter

**意图**：把一个已有接口转换成调用方期望的接口，让不可改的外部实现与内部模型协作。

**适用条件**：
- 外部接口的签名或数据模型与内部期望不一致，且外部不可改（第三方 SDK、遗留 API）。
- 同一转换在 2 个以上调用点重复（能指出调用点）。
- 转换边界清晰：入参、返回值、错误码各有一处映射。
- 外部实现的变更需要被隔离在一处（升级 SDK 只改适配器）。

**不适用边界**：
- 外部接口本可改：先改外部接口，Adapter 只是把坏接口固定下来。
- 只是重命名或纯转发：直接调用更少噪音，多一层会让栈追踪与日志变长，也更容易藏住错误码。
- 转换依赖调用场景：场景差异塞进 Adapter 会让它变成万能适配器，最后谁都不敢改。

**代价与替代**：代价是多一层映射与一个需要跟随外部模型同步维护的边界。更简单的替代是在调用点写转换函数（`to_internal(dto)`）；当转换出现在 2 个以上调用点、且需要统一错误码处理时再抽 Adapter 类。

**wxg 建模示例**：

```json
{
  "node": {
    "id": "pattern:feat-pay:adapter",
    "kind": "pattern",
    "name": "Adapter",
    "attrs": {
      "intent": "把第三方支付 SDK 的接口转换成内部 PaymentGateway 接口。",
      "applicability": "SDK 的签名与内部接口不一致且不可改；to_internal 转换在两个调用点重复；SDK 错误码需要统一映射；SDK 升级频率高于内部接口。",
      "not_applicable": "SDK 接口可改时不用，先改外部接口；只是重命名或纯转发时不用，多一层只会让栈追踪变长；转换依赖调用场景时不用，否则会变成万能适配器。",
      "forces": "外部接口稳定 vs 内部模型稳定；转换集中 vs 调用点简单。",
      "cost": "多一层映射与一个需要跟随外部模型同步维护的边界。",
      "alternative": "先在调用点写 to_internal(dto) 转换函数；转换出现在两个以上调用点且需要统一错误码时再抽 Adapter 类。",
      "source": "GoF (1994)"
    }
  },
  "edge": {
    "kind": "applies",
    "src": "classifier:feat-pay:wechat_pay_adapter",
    "dst": "pattern:feat-pay:adapter"
  }
}
```
- 咬合示例：若外部接口本来就能改、或适配器只是把同名方法转发一遍，判 UNNECESSARY；若图里有适配器节点、代码里调用方仍直接调用第三方 SDK，判 DOC-ONLY。

### Facade

**意图**：为一组子系统提供统一的高层入口，让调用方只依赖用例级操作。

**适用条件**：
- 一个用例按固定顺序调用 3 个以上子系统，顺序与错误处理在多个入口重复。
- 调用方只关心整体成败，不需要子系统细节。
- 子系统 API 稳定，但组合方式容易写错（漏步骤、顺序颠倒）。

**不适用边界**：
- 调用方需要精细控制子系统：Facade 会把控制权藏起来，被迫再加逃生口。
- 子系统只有 1 至 2 个调用：多一层门面只是把调用搬了个家。
- 门面里开始出现业务分支：它已经是用例服务，应改名并配测试，而不是继续当薄壳。

**代价与替代**：代价是一个会随时间膨胀的高层入口，容易变成“什么都往里塞”。更简单的替代是先写一个用例函数（`checkout()`）按顺序调用；等第二个调用方需要同一组合时再抽 Facade。

**wxg 建模示例**：

```json
{
  "node": {
    "id": "pattern:feat-order:facade",
    "kind": "pattern",
    "name": "Facade",
    "attrs": {
      "intent": "为结账用例提供单一入口，调用方不再自己编排库存、支付、通知三个子系统。",
      "applicability": "checkout 按固定顺序调用库存、支付、通知 3 个子系统；APP 与后台两个入口重复同一顺序与错误处理；调用方不关心子系统细节；子系统 API 稳定但组合顺序容易写错。",
```

### Decorator

**意图**：用包装对象在不改原对象的前提下叠加行为，且包装可组合、可嵌套。

**适用条件**：
- 同一横切行为（日志、缓存、重试、鉴权）要按组合叠加到多个实现上，组合在运行期确定。
- 被包装对象有稳定接口，包装只加前后行为、不改语义。
- 叠加顺序影响结果，且顺序需要显式配置（能指出顺序差异导致的测试）。

**不适用边界**：
- 行为是核心逻辑的一部分：包装会把主流程切碎，读代码要沿包装链上下跳。
- 包装层数固定且只有一种组合：直接写一个包住调用的函数即可。
- 需要访问被包装对象的内部状态：Decorator 只能看到接口，会逼你泄漏实现。

**代价与替代**：代价是栈追踪变深、身份与相等判断变复杂（`isinstance` 判断会失效），每层配置要单独管。更简单的替代是显式组合函数（`with_retry(with_limit(fn))`）；需要多层、运行期装配、且每层有独立配置时再上 Decorator 类。

### Proxy

**意图**：用代理对象控制对真实对象的访问（延迟加载、权限、远程、引用计数），调用方仍看到同一接口。

**适用条件**：
- 访问真实对象代价高（远程、磁盘、大对象），需要惰性初始化或访问控制。
- 调用方不应感知代理存在（接口一致），能把代理与真实对象互换。
- 有明确的访问策略：谁能访问、何时加载、何时释放。

**不适用边界**：
- 只想加日志或缓存：Decorator 语义更准确，用 Proxy 会让人误以为有访问控制。
- 代理需要改变返回类型或语义：接口不一致就退化成 Adapter，别硬叫 Proxy。
- 真实对象初始化很便宜：代理只增加一层间接与生命周期 bug。

**代价与替代**：代价是隐藏了对象创建时机与失败点，延迟加载的错误往往在远端点爆。更简单的替代是懒加载属性（首次访问时 `if obj is None: obj = load()`）或显式工厂；需要跨进程、权限或引用计数时再上 Proxy。

## 5. 行为型

### Strategy

**意图**：把可互换的算法封装成对象，让调用方在运行期选择算法，替代按类型分叉的条件分支。

**适用条件**：
- 同一决策点有 2 个以上可替换算法，选型在运行期由配置或输入决定（能举出真实分支）。
- 每个算法可独立测试，且分支会继续增加（已有第二个实现，或下一次迭代明确要加）。
- 调用方只依赖统一接口，不关心算法内部状态。
- 算法之间不共享可变状态。

**不适用边界**：
- 只有 2 个分支且不会增长：`if/else` 或字典映射更短，Strategy 只是把分支搬进类里。
- 分支依赖大量互不相同的上下文：统一签名会塞进一堆可选参数，类型检查形同虚设。
- 选型在启动时固定：在组合根一次决定即可，运行期不必持有策略对象。

**代价与替代**：代价是多一个接口、N 个类与一处选型表，调试要跨文件追。更简单的替代是 `{"a": fn_a, "b": fn_b}[kind]()` 或 `match`；当策略需要独立依赖或生命周期，或分支达到 3 个以上且持续增长时再抽接口。

### Observer

**意图**：定义一对多依赖，主题状态变化时通知所有观察者，让发布者不依赖订阅者。

**适用条件**：
- 一个事件有 2 个以上互不相关的消费者，消费者集合在运行期可变（能指出增删订阅的入口）。
- 发布者不应知道消费者身份与顺序。
- 通知失败不影响发布者主流程，或失败处理已明确（重试、死信、日志）。
- 消费者之间不需要事务一致性。

**不适用边界**：
- 消费者固定且只有 1 个：直接调用函数，Observer 只会让调用链不可见。
- 需要严格顺序或事务一致：多播会让一致性推理变难，应先写明确的用例编排。
- 没有退订与错误隔离：监听器泄漏与异常吞噬会在生产上放大，最后没人知道谁被通知了。

**代价与替代**：代价是隐式控制流（不知道谁会跑）、顺序不确定、错误难归因。更简单的替代是在用例层显式调用 2 个函数，或用简单回调列表；当订阅方确实动态增减、发布者不应感知时再上 Observer。

### Template Method

**意图**：在基类固定算法骨架，把可变步骤留给子类实现。

**适用条件**：
- 多个流程共享同一骨架（3 步以上且顺序固定），差异只在少数步骤（能指出哪些步骤不同）。
- 骨架顺序是业务约束，不能由调用方打乱。
- 差异步骤有统一签名与明确边界，子类只需实现这些步骤。
- 子类数量可控（每个变体一个子类，能列出变体清单）。

**不适用边界**：
- 差异步骤需要不同上下文：基类签名会被撑成万能参数，子类只能忽略一半。
- 变体可以组合出来：继承会把变体锁死，组合更合适。
- 子类按组合爆炸（每加一个可选项就多一个子类）：改用 Strategy 或组合。

**代价与替代**：代价是继承耦合（基类改一步，所有子类受影响），测试要造子类。更简单的替代是把骨架写成普通函数，差异步骤作为参数传入（高阶函数）；只有子类确实共享骨架与状态时才用继承。

### State

**意图**：把对象的状态相关行为拆成状态对象，让状态转换显式化，替代大段状态分支。

**适用条件**：
- 对象有 3 个以上状态，同一操作在不同状态下行为不同（能列出状态与操作的矩阵）。
- 状态转换规则明确，非法转换需要被拒绝（有对应测试）。
- 状态集合稳定或可枚举，转换由事件驱动。
- 状态相关行为占该对象代码的显著部分（能指出分支行数）。

**不适用边界**：
- 只有 2 个布尔标志：`if` 或枚举加小函数更直接。
- 状态与业务数据强绑定、转换分散在多个服务：先收拢转换点（一个函数或一张表），再考虑状态对象。
- 状态对象需要访问大量上下文：会退化成把整个服务塞进状态，此时显式状态机表更清楚。

**代价与替代**：代价是状态对象之间互相跳转，调试要跟踪对象替换。更简单的替代是枚举加一张 `(state, event) -> state` 转换表加一个分发函数；状态行为确实差异大时再抽状态类。

### Command

**意图**：把请求封装成对象，从而支持排队、记录、重放与撤销。

**适用条件**：
- 操作需要排队、延迟执行或持久化重放（能指出队列或日志）。
- 需要撤销或补偿，且每个操作能定义逆操作或补偿动作。
- 调用方与执行方需要解耦（API 层不直接持有领域对象）。
- 同一操作有多种触发来源（按钮、定时任务、重试）。

**不适用边界**：
- 只是把函数包一层：没有排队、撤销、重放需求时，Command 只多一个类。
- 撤销语义无法定义（外部副作用不可逆）：别承诺 undo，改用补偿与审计。
- 操作之间需要强事务：命令对象会掩盖事务边界，应在用例层显式管理。

**代价与替代**：代价是多一层间接，命令对象的生命周期、幂等与序列化都要自己管。更简单的替代是直接调用函数，需要排队时用任务队列加函数引用；需要撤销、重放或审计轨迹时才上 Command。

```json
      "not_applicable": "只是把函数包一层时不用，没有排队、撤销、重放就只多一个类；撤销语义无法定义时不用，外部副作用不可逆就改用补偿；操作之间需要强事务时不用，命令对象会掩盖事务边界。",
```

## 6. 架构与集成型

### Repository

**意图**：用集合式接口表达聚合的持久化边界，让领域层只依赖“取出聚合、保存聚合”，不依赖存储细节。

**适用条件**（真实领域持久化边界，不是 ORM 包装）：
- 领域层有聚合根，用例只按聚合根存取（能指出聚合根与用例）。
- 存储实现可能替换或有多种（数据库、内存、远程），测试需要内存实现。
- 查询语义是领域语言（`find_overdue()`），不是 SQL 片段。
- 事务边界与聚合边界一致，跨聚合查询另有归属。

**不适用边界**：
- 方法只是把 ORM 的 `filter`、`insert`、`update` 逐条转发，方法名与 SQL 一一对应，返回值是 ORM 行对象：这只是多一层壳，调用方仍依赖 ORM 细节，替换存储时一行都省不掉，应直接调用 ORM，或把查询收进用例。
- 报表与列表页的任意组合筛选：用查询对象或读模型，不要为每个筛选组合加 Repository 方法。
- 跨聚合复杂查询：放读模型或专门查询服务；Repository 只服务聚合写入与按 id 取。

**代价与替代**：代价是映射代码与“假装与存储无关”的幻觉，复杂查询迟早泄漏到接口上。更简单的替代是先写一个模块级数据访问函数（`load_order(id)`），让用例依赖它；等聚合边界稳定、且需要替换存储或内存测试时再抽 Repository 接口。

### Unit of Work

**意图**：跟踪一次业务事务中加载或修改的对象，在提交时统一写回，保证一致性与写入顺序。

**适用条件**：
- 一次用例会修改 2 个以上聚合或表，且必须同成同败（能指出事务边界）。
- 修改分散在多个步骤，逐个即时写回会导致中间态可见或重复写。
- 需要延迟写入以合并或排序（先插父后插子）。
- 会话生命周期可被统一管理（请求级或用例级）。

**不适用边界**：
- 只有一个写操作：直接在一个事务里写完，Unit of Work 是空转。
- 存储不支持事务：Unit of Work 会给出虚假的原子性承诺。
- 团队没有统一的会话或生命周期管理：UoW 会变成隐式全局状态，测试与并发都难。

**代价与替代**：代价是会话生命周期、脏检查、提交时机都变成需要解释的机制。更简单的替代是在用例函数里开一个显式事务（`with tx:`）并顺序调用 2 至 3 个写函数；跨多个聚合并需要延迟写时再上 UoW。

### Ports & Adapters

**意图**：把核心业务与外部世界（界面、存储、消息、第三方）用端口隔开，适配器实现端口，核心只依赖端口。

**适用条件**：
- 核心用例需要在不启动真实外部系统的情况下测试（能指出内存适配器或契约测试）。
- 外部依赖有 2 种以上实现或会替换（数据库换代、支付渠道增减）。
- 依赖方向单向：核心不 import 框架与驱动（能检查 import 清单）。
- 有明确的入口与出口边界（HTTP 或 CLI、存储、消息）。

**不适用边界**：
- 小脚本或一次性工具：端口与适配器会把 50 行变成 5 个文件，收益为零。
- 只有一个外部依赖且不会替换：直接依赖加一个薄封装函数即可，不必造端口。
- 核心本身只是 CRUD 转发：六边形会把“没有业务”暴露得更明显，先补业务再谈架构。

**代价与替代**：代价是每个外部交互至少两个类型（端口与适配器）与装配代码。更简单的替代是先用函数边界（核心接受一个 callable 或小的 Protocol 对象），测试与生产各注入一次；当依赖数量与替换频率上升时再正式化端口。

### Circuit Breaker

**意图**：在远程调用连续失败时快速失败并短路，避免故障扩散与线程、连接池耗尽。

**适用条件**：
- 存在跨进程或网络调用，下游故障会拖垮调用方（能指出超时、重试与线程池）。
- 失败可分类（超时、5xx、连接拒绝），且部分失败应计入。
- 有可接受的降级行为（缓存、默认值、排队）。
- 恢复探测可定义（半开状态、探测请求、幂等键）。

**不适用边界**：
- 本地纯函数或内存调用：没有可熔断的故障源，只增加状态机复杂度。
- 没有降级策略：熔断只是把错误换个地方抛，用户看到的是更快的失败，不是可用。
- 写操作幂等性未知：半开探测可能重复提交，需幂等键配合。

**代价与替代**：代价是一个需要调参的状态机（阈值、窗口、半开），参数错了会把偶发抖动放大成雪崩。更简单的替代是先加超时、有限重试与降级默认值；确认下游会长时间不可用、且需要保护调用方时再加熔断。
